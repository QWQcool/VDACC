# MediaGrabber 参考笔记（鸿蒙源码版）

> 来源：朋友提供的 `MediaGrabber 1.0.0` 鸿蒙工程源码（作者已口头授权参考其 UI 代码、文案与素材用于移动端开发；Android / Windows 代码未提供，需自行实现）。
> 本文只记录**交互与信息架构**，不复制其核心引擎与平台适配层代码。内部文档，不公开。

## 1. 它是什么

一句话：**端上本地下载器**——解析和下载都跑在手机里，不需要连电脑。

首屏原话：「本应用在你的手机上本地解析与下载，不需要连接电脑」，支持哔哩哔哩 / 抖音 / 快手 / 小红书 / 森空岛 / 任意网页。

与我们当前方向的差异：

| | MediaGrabber（鸿蒙） | VDACC |
|---|---|---|
| 运行位置 | 手机端本地（JS 引擎 + 宿主桥） | 桌面 core + 本地 HTTP |
| 平台覆盖 | 多平台、含通用嗅探 | 抖音（已通）、网易云（已通）、B站（P5） |
| 深度 | 广度优先 | 契约/质量/可编程优先（Skill、SSE、批量） |
| 引擎 | 自带 JS bundle | Python + yt-dlp |

结论：**它是"手机上的万能下载器"，我们是"桌面上可被 agent 调用的下载内核"**。两条路线不冲突，移动端应该做遥控而不是移植。

| 区块 | 内容 | 备注 |

## 3. 素材条目模型（值得抄的部分）

一条素材的展示信息由**能力位拼装**，不是简单一行标题：

```
[图标] 文件名.ext
       HLS · 纯音频 · DASH 合并(预估 86MB) · 1080P · 42.1MB
```

字段大致是：`filename / ext / kind / qualityLabel / size / playlist(hls) / mergeAudio{url,size} / audioOnly / httpHeaders`。

三个细节值得直接借鉴：

1. **合并体积预估写在条目里**：`mergeAudio` 存在时显示「预估 X MB，将合并」；超过阈值显示「超过阈值，将分别保存」。
2. **未知就是未知**：体积拿不到时不隐藏，而是提示「体积未知，将尝试合并（可能占用较多内存）」。
3. **条目可整行点击**，不只是点复选框；点完立刻更新底部按钮的计数。

## 4. 移动端特化：120MB 拆轨（最有价值的一条）

核心层的合并是「整文件读入内存再写出」，峰值约 2× 文件体积。手机 WebView 堆远小于桌面，300MB 档位实测会 OOM 崩页面。

他们的做法：**预估音视频合计 > 120MB 就不合并**，拆成「标题_视频」+「标题_音频」两个文件，并在警告里说明原因与阈值。

对我们的启示：

- 我们桌面端是**流式落盘**，不存在这个内存问题，不需要照搬阈值；
- 但如果将来做端上实现（TS/ArkTS），这条必须保留；
- 更通用的做法是：**把"是否合并"变成契约里的一个能力位 + 可读原因**，而不是 UI 里硬编码。

## 5. 平台桥的设计（如果做鸿蒙端）

- `globalThis.__MG_PLATFORM__` 在 bundle **之前**注入，`platform-resolve.js` 用 getter 延迟绑定；
- ArkWeb 用 `javaScriptProxy` 暴露方法，参数/返回值统一走 **base64**（二进制不可靠）；
- ArkTS 侧异步完成后 `runJavaScript` 回投 `MGBridgeDeliver`，JS 侧 Promise 兑现；
- 超时分两档：普通 30s、HTTP 600s（30s 会把大文件下载判死）。

这套模式很稳，但**我们不需要它**——我们的 core 不在端上，移动端只要 HTTP 客户端。

## 6. 可直接借鉴的 7 个点

1. **底部固定操作栏 + 计数**：移动端比"每行一个下载按钮"更好用。
2. **能力位拼装文案**：把"能不能合并/是不是 HLS/体积是否已知"写成一行，比只写分辨率诚实。
3. **警告分两层**：解析警告（结果区）与任务警告（进度区）分开，互不覆盖。
4. **行内输入反馈**：粘贴后立刻告诉用户"识别到几个链接"，而不是等他点解析。
5. **封面加载失败即隐藏**：不占位、不显示破图。
6. **`data-i18n` 属性驱动的 i18n**：文案与 DOM 解耦，切换语言不用重排结构。
7. **状态圆点**：本地运行状态用「点 + 文案」，比 toast 更持久。

## 7. 不照搬的 4 个点

1. **默认全选**：他们默认全选所有素材；我们默认只选推荐档（避免误下 N 份大文件）。
2. **端上引擎**：不做，移动端走遥控。
3. **强制通用解析**：我们还没做 L2，保持置灰 + 「未实现」，不放假按钮。
4. **开屏授权页**：他们用了第三方开屏组件（MIT），我们不需要。

## 8. 移动端方案结论（承接讨论）

| 方案 | 判断 |
|---|---|
| 遥控客户端（手机连桌面 `vdl serve`） | **推荐**，所有引擎可用 |
| 端上移植（抖音 + 网易云） | 仅在"移动端是主战场"时做；B站 不可移植（依赖 yt-dlp） |
| 云端核心 | 不做（带宽 + ToS） |

需要提前在 `vdl serve` 里预留的两件事：**局域网监听 + 二维码/token 配对**；其余（SSE、任务模型）已经具备。
